## 0. 使命一句话

`memstrata` 是**为"可控生成"服务的记忆管理与上下文组合方案**：把一部长视频里出现过的
实体（character / prop / location）沉淀为一个**结构化的记忆库** \(\mathcal{M}_n\)，并在每个
生成步为"点名到的实体"组合出**最小而充分**的视觉上下文，让下游生成器稳定复现同一实体。

记忆库不是"帧的仓库"，而是"**每个实体一份、可被生成条件化的身份档案**"。

---

## 1. 六条不可让渡的库质量公理

记忆库在任意时刻都必须同时满足下面六条。它们是所有准入 / 去重 / 淘汰 / 组合逻辑的**目标函数**：

1. **结构化（Structured）**——每条视觉证据是带闭集标签的分层记录
   `[image + spatial_angle + state_angle + shot_size + lighting + temporal]`，
   而非裸图；身份、类型、生命周期都是 typed 字段。**没有非结构化的角落。**
2. **低冗余（Low redundancy）**——同一实体、同一视觉分层桶不保留两条几乎一样的证据；
   近重复 embedding 直接丢弃。库的每条 rep 都要"挣得自己的位置"。
3. **高聚合（High aggregation）**——同一身份的所有证据聚到**同一个 asset** 下（命名锚定），
   不因换装 / 换角度 / 换场景就裂成多个实体。一个实体 = 一份档案。命名锚定是**别名感知**的：
   同一身份的不同称呼（"the priest" / "Father Janovich"）经 `metadata.aliases` 归到同一 asset
   （`bank.find_by_name` / `register_alias`，读写路径对称），但**只认显式别名、不做模糊自动合并**。
4. **低混杂（Low mixing）**——一个 asset 下**只能有同一个身份**的证据。绝不允许"另一个长得像的人 /
   另一件相似道具 / 看不清是谁的碎片"混进某个实体的档案。**这是记忆库的第一红线**——
   混杂会直接毒化下游生成（生成出"四不像"的角色）。
5. **同实体高多样（High intra-entity diversity）**——在低混杂的前提下，主动保留同一实体的
   **不同相机视角（front/side/back/top）、不同姿态（pose: standing/sitting/lying/action）、
   不同外观状态（default/changed/damaged）、不同景别 / 光照**。这些是去重的分层桶维度
   （`_attr_bucket` = spatial×state×shot×lighting×**pose**）；pose 为**可选轴**，缺失记 `unknown`
   不减粒度，出现时防止"同实体不同姿态"被当近重复丢掉。多样性是"跨视角 / 跨状态召回"的燃料。
6. **高效上下文组合（Efficient composition）**——组合是**确定性、model-free**的解引用：
   显式 id → aspect/function 过滤 → 偏好角度/状态命中 → 最新 chunk；只给下游**用得上的最少证据**，
   不做全库相似检索、不返回全部资产。可配 `context_rep_budget` 硬上限：先砍关系扩展的连续性证据，
   再砍点名实体的多余 rep，但**永不砍掉某个点名身份的最后一条 rep**（丢身份比超预算更糟）。

> 记法：**4 与 5 是一对张力**——"低混杂"要求收紧准入，"高多样"要求放宽保留。
> 二者的分界线是**身份**：*同一身份的不同呈现要尽量收*（多样），*不同身份/不可辨识的碎片要坚决拒*（不混杂）。
> 一切准入逻辑都在这条线上做文章。

## 2. WHO 先于 WHERE（准入控制的核心原则）

记忆库最容易犯的错，是把"**这张 crop 该放哪个桶（WHERE：角度/状态/景别）**"当成了全部，
而漏掉了"**这张 crop 到底是不是这个实体、看不看得清（WHO）**"。

- 纯角度/embedding 去重只解决 WHERE：它会**开心地收下一个换了角度的混入实体**，因为它"填了一个新桶"。
- 因此准入必须**先过 WHO，再谈 WHERE**：一条证据只有在"确实是本实体、且身份可辨识"之后，
  才有资格参与角度多样性的保留竞争。

落地为三道互补的准入闸（从最便宜到最贵，命中即止）：

| 闸 | 抓什么 | 手段 | 成本 |
|---|---|---|---|
| **① 确定性暗/低信息门禁** | 近黑、近平、无信息的碎片 | 蒙版实体像素亮度均值/方差（`lib/crop_quality.py`） | 纯确定性，不调模型 |
| **③ 身份可见性（identity_visible）** | 后脑勺/背影、严重模糊、遮挡到看不出是谁 | **复用已有的 crop 属性 VLM 调用**多返一个布尔字段 | 零额外请求 |
| **② embedding 内聚度** | 同名但不是同一个人/物（跨 crop 混入） | 新证据与本 asset 可见簇的余弦内聚度（`lib/dedup.medoid_cohesion`） | 复用已存 embedding，不调模型 |

三道闸对应公理 4（低混杂），且刻意**不误伤公理 5（高多样）**：
- ①只杀"没信息"的（暗/平），不碰暗但有结构的正常低光镜头；
- ③把"看不清身份"的 crop 降级为**非身份锚**（不当参考），但**仍作为跨视角多样性保留**
  （背影是合法的 `spatial_angle=back`，不能因为是背影就丢）；
- ②只在"身份可见"的证据之间比对，且需要已有稳定簇（≥N 条锚）才启用，避免把同一实体的
  合法侧脸/侧身当外人拒掉。

### 2.1 入库闸之外：库级 cohesion 自审（回溯式第四道闸）

三道入库闸只守**新进证据**，守不住两种"已污染"：**首帧就是内鬼**（②还没有稳定簇可比），
以及在②启用前混进来的历史证据。因此补一道**周期性库级自审** `AssetCurator.audit_cohesion`：

- 逐 asset 取"身份可见 + 未废弃 + 有 embedding"的 rep，算 `medoid_cohesion`——medoid 是
  多数身份质心；到 medoid 相似度 < floor 的 rep 判为疑似**异身份内鬼**。
- 保守隔离（§4）：命中者**打 `deprecated_by="cohesion_selfaudit:*"` 废弃并留痕**，从此不进
  `compose`（停止毒化生成），但**不删除、可回退**；`isolate=False` 只出报告不动库。
- 与②同源：floor≤0（离线 HashEmbedding）时**整体空转**；生产用真实 encoder 并按控制集校准。

## 3. 命名锚定 vs. embedding：各自的边界

- **身份分配永远由命名信号锚定**（`AssetCurator._resolve_asset`）。embedding **不**用来"重新决定这是谁"
  ——那会破坏可复现性与 Bench 契约。
- embedding 的合法职责扩展为两项，均为**门控（gate），非身份分配（assignment）**：
  1. 低冗余门控（近重复丢弃、farthest-point 多样性选择）——原有职责；
  2. **准入一致性门控**（②：新证据与本 asset 已有可见簇是否内聚）——本次扩展。
- 二者的共同点：它们只回答"**这条证据要不要收 / 能不能当锚**"，从不回答"**这条证据是谁**"。
  身份始终是名字说了算。

---

## 4. 保守优先：拒绝 vs. 隔离

- Bench（gold 构造）侧对混杂**硬拒**（`accepted=false`），因为 gold 要绝对干净。
- SUT（本包）侧默认更**保守可复现**：
  - ①确定性暗门禁：证据无信息 → **拒**（不占库容）。
  - ③身份不可见：**不拒、降级为非锚**（保留多样性价值）。
  - ②低内聚：默认**关闭**（`cohesion_floor=0`，因离线 HashEmbedding 无语义）；生产用真实
    encoder（DINOv3/ArcFace/VPR）时**显式开启**并按控制集校准阈值，命中按需**拒或隔离**。
- 原则：**能确定性判死的就确定性拒；有语义歧义的宁可降级/隔离并留痕，也不静默删证据。**

## 5. 与 Bench 的关系

- `memstrata`（SUT）**零 import `vmem_bench`**（基准）；共享的 crop 质量/属性逻辑各存一份镜像（如
  `lib/crop_quality.py` 之于 bench `crop_qa.py`），契约对齐、代码不交叉。
- Bench 评测协议**已冻结**：本包可**消费**可选字段、可增强内部能力，但**不要求** Bench 新增
  标注轴或指标。库质量的增强是"方法侧变强"，不是"改考卷"。

## 6. 自检清单（改动记忆管理代码前必读）

任何触碰 `bank/` / `steps/curate.py` / `steps/compose.py` / `lib/dedup.py` / `llm/crop_attributes.py`
的改动，都要能回答：

1. 它让六条公理里的哪几条更好？有没有牺牲另一条（尤其 4↔5）？如何权衡？
2. 它是 WHO 层还是 WHERE 层？WHO 的判断有没有走"先可见、再一致"的顺序？
3. 它有没有把 embedding 从"门控"越界用成"身份分配"？
4. 离线默认（HashEmbedding / null classifier）下行为是否不变、测试是否仍绿？
5. 它对下游 compose 的"最小充分上下文"是更省还是更肿？
